# x50-patch-switcher

A small C++17 / Qt 6 Widgets desktop app that finds and selects programs and
combinations on a **KORG X50** over USB-MIDI, with a full-screen **live view** of 6-8
large buttons for the sounds of the current set. Built for Chroma Noir's support
keyboard player, who runs it on a **Windows** laptop. Windows is the primary target;
Linux and macOS build too. Works fully offline. No editor, never writes to the X50.

## Read in this order

1. `docs/SPEC.md`: behaviour and architecture. The authority for what is correct.
2. `docs/MIDI.md`: every byte sent and parsed, with its source in Korg's documents.
   Hardware facts not yet verified are marked; gates G1 and G3 verify them.
3. `docs/PLAN.md`: milestones, tasks, acceptance criteria, gates, Decisions log. The
   foreman ticks it.
4. `docs/DESIGN-BRIEF.md`, then `docs/design/DESIGN.md` once it exists: everything
   visual. The builder does not invent visuals.
5. `docs/FOREMAN.md`: how the coordinating session works.

Korg's source documents are on the owner's machine, not in git (paths in
`docs/MIDI.md`). Read them by path; never copy them into the repository.

## Build, test, run

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release     # first time fetches RtMidi 6.0.0
cmake --build build -j
ctest --test-dir build --output-on-failure          # headless; tests set QT_QPA_PLATFORM=offscreen
./build/x50-patch-switcher --list-ports
./build/x50-patch-switcher --fake-midi              # the GUI against the simulated X50
./build/x50-patch-switcher --probe --fake-midi
```

Linux box: Ubuntu 24.04, Qt 6.4.2 (`qt6-base-dev`), GCC 13, ALSA. `aseqdump` and the
ALSA `Midi Through` port are the hardware-free MIDI test path. Windows builds come only
from CI.

## Conventions

- C++17, Qt 6.4 API floor, Qt Widgets only. No QML. No dependencies beyond Qt and
  RtMidi. No network code of any kind.
- One class per `.h/.cpp` pair under `src/<module>/` (`app`, `core`, `midi`, `ui`).
  `QStringLiteral` for literals; `QT_NO_CAST_FROM_ASCII` is on.
- Every `core/` and `midi/` behaviour has a Qt Test in `tests/`, run against `FakeX50`
  where MIDI is involved. Add tests with `x50_add_test(name sources…)`.
- All bytes are built and parsed in `X50Protocol` and nowhere else.
- RtMidi callbacks arrive on RtMidi's thread: marshal with a queued signal, never touch
  widgets there. Port open and send can throw `RtMidiError`: catch, report in status,
  never crash. Nothing waits on MIDI on the GUI thread.
- MIDI is sent only on an explicit action (Enter, double-click, Play, a live button or
  key, prev/next, `--send`). Never on highlight.
- Live view shows no dialogs and never leaves on a single keypress.
- Footprint: no timer under 2 s except request timeouts and the Esc-hold timer; no
  repaint without a state change; no allocations in paint paths.
- `data/x50-factory.tsv` is generated by `scripts/extract-voice-list.py`; edit the
  script, not the file.
- Nothing trademarked under `assets/` (no KORG logo). `assets/local/` is git-ignored.
- Commit messages `M<milestone>.<task>: <what>`; the foreman commits, agents do not.
- No em dashes in user-facing strings or docs.

## Hardware facts you must not get wrong (details in docs/MIDI.md)

- Everything goes on the X50's **global channel**; SysEx header `F0 42 3g 7A`, `g` =
  channel − 1. Discover it from the Device Inquiry reply.
- Program and combination banks A-C use the **same** bank select bytes; the X50's mode
  decides which is selected. Switching between them needs **Mode Change**
  `F0 42 3g 7A 4E 0m F7` (m = 0 COMBI PLAY, 2 PROG PLAY) before the bank select.
- Bank select MSB depends on the X50's **Bank Map**: `00` (KORG) or `3F` (GM) for banks
  A-D; `79` for G, `78` for g(d) in both maps. Read the map from Mode and State
  (`12` → `42`, byte 7 bit 4). Never assume it.
- Order: [Mode Change, wait ACK or 100 ms], CC0, CC32, PC.
- The app never sends parameter changes, write requests or dumps **to** the X50.
- The owner has no X50. Hardware truth comes from `--diagnose` runs by the keyboard
  player (`docs/gates/`); until a fact is marked verified there, code must validate
  replies strictly and report raw bytes rather than guess.
